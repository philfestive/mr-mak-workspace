# Mr. Mak launch and MCP inventory review

Reviewed 2026-10-12. Scope: checkout source and the specifically authorized local account-launcher source. No credentials, transcripts, account contents, running service, or installed application payload were inspected. No launch, probe, configuration change, restart, installation, or Git write occurred. Current organization is Workspace Home; the older Team Hub references in T005 await coordinator reconciliation.

The main finding is a scope mismatch: the desktop launcher permits each chat to use another working folder, while its MCP panel scans the Workspace repository and service environment. Local account wrappers select isolated homes, but normal desktop source does not invoke those wrappers or select a profile.

## Observed launch behavior

- New chat sends agent, cwd, bypass and resume ID; it offers no account selector (`src/desktop/Chats.tsx:12-34`). Session metadata likewise has no account/profile field (`desktop/service/sessions.mjs:18-20,94-102`; `src/desktop/types.ts:3-11`).
- Launch creates its environment from the **Workspace** repository, then starts the CLI at **session.cwd** (`sessions.mjs:124-138`). `agents.mjs:87-99` inherits process environment, adds only `MRMAK_MCP_*` values from Workspace `.env`, and removes selected host identity variables. It does not read the chat project's `.env`. General API keys already present in process environment remain inherited; the filter applies to added file values.
- CLI arguments cover permission mode, resume and effort, without a Codex `--profile` argument or account-home assignment (`agents.mjs:56-84`). A caller-supplied `CODEX_HOME` or `CLAUDE_CONFIG_DIR` can still propagate through inherited environment. Presence of `.mrmak/accounts` alone establishes no desktop integration.
- The Codex coordinator separately uses `codexBinary()`, Workspace cwd and the same child environment (`desktop/service/coordinator.mjs:76-99`). On Windows, `codexBinary` prefers npm package binaries before its fallback, while terminal commands use PATH/search-root resolution (`agents.mjs:34-53,58`; `desktop/service/platform.mjs:21-39`). These routes may select different CLI versions.

The local `.mrmak/agents/Start-Account.ps1` **does** use `.mrmak/accounts/<profile>` (`:73-85`). It supports four named Codex/Claude profiles, checks account-folder ACL protection, selects an executable, and sets `CODEX_HOME` or `CLAUDE_CONFIG_DIR` (`:87-120,131`). Codex gets file-backed credentials, ChatGPT login and no-daemon arguments; provider overrides are cleared (`:100-119`). It runs from the Workspace root and restores its environment afterward (`:128-148`). Its Codex resolver prefers the standalone installation (`:17-27`). This is a separate local wrapper, not the desktop GUI launch path. Successful login or wrapper execution remains unverified.

## Observed inventory and probe behavior

`server.mjs:40` constructs one `McpInventory(repo)`; `/api/mcp` and `/api/mcp/check` accept no session, project or account context (`:213-214`). Inventory uses service `CODEX_HOME`/`CLAUDE_CONFIG_DIR` or OS-home defaults and fixed Workspace project paths (`desktop/service/mcp.mjs:30-61`). It covers Codex, Claude, Kimi and Cursor, but no OpenCode. It does not resolve Codex named profiles, ancestor project layers, project trust or all policy sources; therefore its merge is an approximation requiring client-specific verification (`:63-80`).

Codex plugin discovery selects the highest directory name, rather than proving the active installed version (`mcp.mjs:85-98`). Claude discovery uses its installed-plugin registry (`:100-109`). Both mark plugin entries managed, and direct Codex `node_repl`/`cua_repl` entries are also protected (`:98,109,123`). Managed entries cannot be checked (`:151,168`). This conservative protection should remain; distinguish host-owned transport from portable plugin metadata before widening probes. The empty `IntegrationManager` instantiated by the service is a separate binding/event abstraction, not an MCP relay or connector activation mechanism (`server.mjs:39`; `desktop/service/integrations/manager.mjs:4-24`).

Inventory interpolates **every** Workspace `.env` value, unlike CLI file forwarding (`mcp.mjs:111-126`). Its stdio probe environment is separately constructed from SDK defaults, explicit server env and `env_vars` (`:154-156`), creating another possible launch/check mismatch. `http_headers_helper` disables checks without a dedicated readiness explanation (`:142,151`). URL origins, executable basenames and credential names are exposed, while values and secret URL components are withheld (`:140,148-150`).

Check opens a separate temporary transport, initializes MCP and lists the first tool page; it never calls a server tool (`mcp.mjs:182-197`). Results expire after five minutes and are invalidated by configuration fingerprint changes (`:143-145`). Authentication errors receive fixed status text; no agent credential store or OAuth provider is supplied (`:185-190,198-202`). Inspector-owned stdio trees are terminated and HTTP sessions closed (`:203-210`). This proves inspector connectivity at that moment, not tools loaded or authorized in a particular agent. Starting a configured executable can itself have side effects despite the absence of tool calls.

UI footer explains the separate connection, but the headline says "Tools available to your agents" without account/cwd context (`src/desktop/McpPanel.tsx:52,76`). OpenCode is launchable, detects major version and injects its observer into `OPENCODE_CONFIG_CONTENT`, while the MCP UI omits it (`desktop/service/opencode.mjs:13-44`; `McpPanel.tsx:9-14`). A generic `/mcp` button also needs client-specific instructions.

## Version boundary

Checkout and Tauri declare 0.5.1 (`package.json:4`; `src-tauri/tauri.conf.json:4`), while update instructions still name 0.5.0 (`docs/updating.md:10`). Native startup prefers bundled `runtime/service/main.mjs` when bundled Node exists, otherwise checkout service source (`src-tauri/src/main.rs:209-223`). Packaging copies source into that runtime (`desktop/prepare.mjs:30-38`). Thus this review cannot establish installed or running behavior from checkout alone. These differences are evidence gaps, not proof of a faulty installed version.

## Bounded implementation handoff, proposed only

1. Add one explicit launch-context resolver for executable, client/version, account ID, home and project cwd. Wire `agents.mjs`, `sessions.mjs`, `coordinator.mjs`, `server.mjs`, `native-events.mjs` and `codex-history.mjs` to that context; persist non-secret profile identity for correct resume/history. GUI account selection requires `Chats.tsx` and `types.ts`. Preserve default behavior until an account is selected; never copy login stores.
2. Make inventory session/project-aware using the same resolved context. Add verified client adapters, including OpenCode; retain unsupported or unknown scopes visibly. Correlate check cache by client, account, project, executable/version and effective configuration. Resolve plugin versions from authoritative activation evidence; preserve host-managed no-probe rules.
3. Align credential/environment semantics, label configuration versus inspector handshake versus agent-native proof, and add runtime provenance to service diagnostics. Permit sensitive companion/runtime probes only through an explicit bounded owner workflow. Keep native authentication status in its own agent.

Acceptance checks should use fake homes, two accounts, two projects and injected spawners/probes: selected context must reach launch, inventory, transcript lookup and resume without crossing accounts; Workspace env must not satisfy another project's check accidentally; ambient sensitive-key policy must be explicit; cache must invalidate on context changes; managed/OAuth/helper entries must not spawn; secret-bearing failures must remain redacted. Add OpenCode v1/v2 configuration fixtures and packaged/source provenance fixtures. Existing tests cover precedence, secret redaction, handshake-only checks, process reaping and credential invalidation (`desktop/service/test/mcp.test.mjs:19-130`), but not account/project launch parity. No tests were run in this source-only review.
