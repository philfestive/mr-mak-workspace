# Lane 22: Everyday operating practice

Planning proposal, 2026-10-12. Use shared core guidance and only the tools needed
for the current project. These practices create no permanent roster, account,
model selection or standing twelve-agent requirement. No connections were tested
or changed in this lane.

## Startup and resume

1. Read the current request, machine rules, local AGENTS.md, owner context and
   project brief. Start from [Workspace Home](../../../../../workspace/2026-10-12_workspace-home/overview.md).
   Use its Tasks for this repository; external projects keep their local boards.
2. Confirm the absolute working folder, required result, allowed files and
   operation scope. Re-read ownership immediately before editing shared files.
   One writer owns each shared file; workers return evidence in assigned reports.
3. Identify the actual client/version, launcher, selected account alias, effective
   configuration home, profile and overrides. Record unresolved facts as unknown;
   numbered account folders and earlier inspector results do not identify a chat.
   Keep private bindings and identities outside tracked notes.
4. Match required capabilities to the relevant repository skills and exposed
   tools. A skill supplies instructions; it does not install or authenticate an
   MCP. Read the chosen skill before acting. Use inherited model, effort and
   permissions unless the owner has selected a change.
5. Compare the handoff with current files and tool exposure. Continue useful work
   within authorization when a tool is unavailable; record the exact missing
   prerequisite and next owner. Reconnect, account switches and project changes
   require fresh qualification before relying on previous connection evidence.

The [organization process](../../../../../processes/workspace-organization.md)
owns this short loop. Home indexes briefs and evidence; it does not duplicate
project specifications. Update the existing task's status and Notes only within
the assignment. A roster, separate handoff and independent reviewer are optional
unless the task or project requires them.

## Evidence, paid work and change review

Keep desired, configured, enabled, exposed, inspector-checked, authenticated,
project-bound and native-consumer-verified observations distinct. A check records
UTC time, actual client/version, account alias, configuration context, working
folder, method, result and limits. Preserve historical evidence with a stale
reason when its context changes. Do not rerun costly checks solely for ceremony.

Use an authorized, harmless native operation when connection proof is necessary.
Verify project binding before project operations. Runtime control belongs to the
named project owner; preserve the one-Godot-process rule. Tool access alone does
not authorize installation, sign-in, restarts or paid generation.

For paid work, keep provider, selected model, budget and job ID in the existing
private receipt location. After a timeout, inspect or resume that job before
submitting another. Store only a redacted outcome and evidence reference in Git;
never publish tokens, raw responses, transcripts or receipts.

Review the actual diff and run checks appropriate to the changed behavior.
Separate planned changes, implementation, technical verification and owner
acceptance. Before a requested commit, review exact selected files for secrets,
personal data and unrelated changes; stage only those paths and check the staged
diff. Git writes use the required maintenance-disabled prefix. Push requires the
named repository/branch or applicable standing grant and a read-only origin
check; never push main. Organization work grants neither commit nor push.

```text
Inherited model, effort and permissions; selected paid budget if relevant:
Required capabilities, skills and connection IDs:
Tools exposed now; dated validation context; unresolved prerequisites:

```

Launch the smallest useful wave after its dependencies are met. Twelve workers
apply to the owner's current planning request, not every future task. A setup
packet must name the actual target and activation authorization before execution.

## Maintenance and handoff

Refresh relevant evidence after client/plugin/runtime version, configuration,
account/profile, launcher or project-binding changes, authentication failure or
reconnect. Review obsolete links when moving documentation; retain history and
stable IDs. Do not sweep drives or retire repositories as routine maintenance.

Handoff the result, owned paths, checks, unresolved dependencies, preserved
sessions/jobs and one concrete next action to the next owner. An unfamiliar agent
should find the authoritative board and exact working folder, identify its tools
and resume without guessing an account or repeating a paid job.
