# Character pipeline

Idea -> versions -> refinement -> editable source -> named export and consumer
proof. Each stage leaves a result you can open and a clear next decision.
Choose the output needed now, then continue when the next stage is assigned.

[Characters](#/character-lab/1) shows the work. [Overview](#/character-lab/0) explains
the lab's goals, and [Lessons](#/character-lab/2) records what earlier runs taught us.

## Outputs and stage exits

- **Idea:** a short brief with intended use and selected references. Move on
  when identity, use and the next design question are clear.
- **Versions:** named alternatives from an exact base, with prompts and a
  comparison. Record what each result preserved and changed.
- **Refinement:** an exact chosen reference and its selection reason. Record
  what to keep, what still needs work and the next deliverable.
- **Editable asset:** native source and a viewable sprite, illustration or model
  matching the chosen reference. Review required shapes, details and intended use.
- **Named delivery:** an export, its destination record and receiving evidence.
  Name the project/owner; show the actual consumer using the export and the
  required result.

Reference sheets, materials, rigging and animation are scheduled when the named
output needs them. A choice applies to its own stage. A chosen concept records
the design direction; the receiving project's evidence establishes actual use.

For 2D, the route can be concept -> sheet/sprites -> animation -> engine. Name
canvas/frame dimensions, pivot, palette/filtering, atlas layout and timing when
the consumer needs them. For 3D, add mesh, materials, rig and clips as required.
Clay describes a look or construction family; stop-motion timing is a separate
choice. [Styles](#/character-lab/4) and [Directory](#/character-lab/5) keep those
choices separate from project and source ownership.

## A repeatable version round

Keep each round in the character's existing card and revision records. Present
the question, reference, prompt, comparison and choice together.

- **Question:** the design decision this round should resolve.
- **Exact base:** the image or revision used, with its source.
- **Keep / Change:** features to preserve and deliberate changes.
- **Named alternatives:** descriptive names linked to exact outputs.
- **Observed result:** what each output preserved, changed or missed.
- **Choice:** the exact chosen output and reason, or an explicitly open choice.
- **Next deliverable:** what to produce, where it belongs and what will finish it.

Ask focused questions, compare alternatives suited to the question, then choose,
revise or leave the choice open. The amount of generation follows the selected
task, model and authorized budget. Record the provider and model actually used
with the prompt so a useful result can be reproduced.

The separate Arachne sample illustrates this sequence. Version 8 explored craft
materials, costume, painting language and a larger redesign. Version 9 used the
exact Version 8 Grok A output as its working base for palette alternatives. That
names a carried-forward reference; a recorded owner choice establishes selection.
Its blue-skin alternative changes the purple skin of that base, so the observed
result should describe the change even though the prompt calls it preservation.

## Where the asset goes

Keep this destination record with the asset deliverable. Use exact files and
leave unresolved fields visible until the destination is chosen.

- **Editable source:** the native source file and retained location.
- **Export:** the exported file and intended format.
- **Receiving project and owner:** named project, working folder and receiving owner.
- **Consumer:** the scene, asset record or other file that uses the export.
- **Evidence:** the receiving capture or verification record, with date and limits.

Arty, CX20 and CX30 are historical examples of named model work and destinations.
They do not identify a current lab selection, export path or receiving project.
An assigned delivery names its actual source, export, consumer and proof.

Use the [delivery template](../../projects/character-lab/templates/model-handoff.json).
The compatibility name supports sprite bundles as well as models. Planned,
delivered and verified states describe this one named receiver. Verification
retains evidence for every declared export, including required metadata sidecars.
