# Target setup

Use a small shared core and explicit project/role additions. Keep actual
configuration and authentication in the selected client's supported stores.
Maintain reviewed definitions, version records and guidance here.

## Shared core

Core includes the machine safety rules, current organization entry point,
repository skills, source inspection and available host-managed browser/Node
tools. Host-managed tools remain installed and maintained by their host.
An official documentation connection is a candidate core addition, subject to
the selected client's supported setup and verification.

| Profile | Additions | Operating boundary |
| --- | --- | --- |
| Research/review | Official documentation and selected read-only evidence tools | Assigned report and named sources |
| Development | The selected repository's development tools | Exact files and acceptance checks in its task brief |
| Godot observer | Qualified project-bound observer and retained artifact route | That project's observer authority and runtime owner |
| Godot operator | Supported runtime/editor route | Separate named owner, authorized operations, one Godot process |
| Creative production | Selected imagegen/fal/Higgsfield route and required local tooling | Chosen provider/account, output scope and generation budget |
| Blender authoring | Verified Blender executable and authoring workflows | Editable sources, exported assets and required engine review |

A profile is a capability request, not a permanent agent, account or automatic
permission grant. Configuration reuse does not imply credential reuse.

## Canonical sources

| Information | Home |
| --- | --- |
| Current task status and decisions | Workspace Home |
| Setup specification and readable results | This MCP setup card and linked project sources |
| Project workflows | `.agents/skills/`; generated `.claude/skills/` mirrors |
| Reviewed plugin source and version | Owning source repository/catalog |
| Actual client/account/project configuration | Its existing supported configuration scope |
| Logins, OAuth tokens, caches and runtime state | Private client-managed local storage |
| Account/project path bindings | Private local binding map, with tracked aliases only |
| Per-task evidence and reviewer findings | Assigned task report; consolidate through one writer |

Track a schema version, stable connection ID, client/profile/project aliases,
purpose, scope, source/version, transport, prerequisite names, auth kind,
desired state, observed configuration, validation method/time/context, owner and
next action. Export allowed metadata only; never raw environment values,
command arguments, headers, signed URLs, account identities or native auth files.

## Account and application alignment

Resolve executable/version, client, account home, selected role and project cwd
once per chat. Use that same context for launch, inspection, history and resume.
Preserve the default route until an account is explicitly selected. The local
wrappers and desktop source currently differ; application work is proposed.

The MCP panel should show **declared**, **locally prepared**, **inspector checked**,
and **native-session verified** separately. It needs client-specific config
adapters, correct plugin selection and checks that expire when context changes.
OpenCode, Kimi distribution differences and Cursor interpolation need explicit
coverage rather than assumed compatibility.

## Creative and Godot reconciliation

Current fal guidance proposes an OAuth relay for new MCP setup, while repository
templates use an older Bearer route. Reconcile those sources in a dedicated
packet; neither source comparison nor this review proves the older endpoint
broken. [Official fal MCP guide](https://fal.ai/docs/documentation/setting-up/mcp).

Maintain separate Pilot, GodotWorld3d and EduAarpg bindings. Runtime owners perform
approved capture/export/control; other agents consume correlated source and
evidence. This serialized operating model does not establish that the current
gateway supports arbitrary concurrent clients.

Codex supports user and trusted project configuration; local clients share
those layers, while hosted web use has its own plugin context. Validate the
actual client and launch route. [Official OpenAI MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).
