# MCP startup for an assisting agent

Start with current machine/repository rules, owner context and
[Workspace Home](../workspace/2026-10-12_workspace-home/overview.md). Read the
selected project's brief and authoritative task status before editing.

Use the [MCP setup report](../workspace/2026-10-12_mcp-setup/overview.md) for setup
architecture and [Agent startup](../workspace/2026-10-12_mcp-setup/agent-startup.md)
for the reusable brief. [Delivery waves](../workspace/2026-10-12_mcp-setup/waves.md)
owns the implementation sequence; it is a proposal until its work is assigned.

The owner chose a shared core plus tools matched to each project or role.
Resolve the actual client/version, account home, role and project folder. Compare
required capabilities with tools exposed in the current session. A different
account, cached plugin or older connection receipt does not prove readiness.

Keep real configuration and logins in their owning client scopes. Keep external
projects and their rules in place. One writer owns each shared file and Git
index; worker output goes to its assigned paths. Use subagents only when the
owner or applicable instructions ask for them; the two 12-agent review waves do
not create a standing staffing requirement.

On a mismatch, record the exact missing dependency and continue independent
authorized work. Do not switch accounts, copy credentials, launch a runtime,
enable a server or restart an active app merely to satisfy this process.
At handoff, record source state, exact edits, actual checks, evidence limits,
remaining work and the next owner. Task status remains in Workspace Home or the
selected external project's own board.
